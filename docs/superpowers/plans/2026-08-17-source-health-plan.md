# 实施计划：源生态达标——让「能搜到就能读」成为默认

日期：2026-08-17（规划于 08-16 晚，目标已与用户对齐）
状态：待开始
经验引用：lessons 3.39（不可用源分类与排除）、3.40（批量检查限流误报）、3.1（真实源测试驱动）、2.3（偶发失败判断）。

## 迭代目标（用户确认）

> 让「能搜到就能读」成为默认：常用书源 搜索→目录→正文 全链路可用；
> 不可用源全部排除；检测能力产品化（GUI 一键发现"能搜到但读不了"的源）。

每个目标都有**完成标准**（可衡量）与**验证方式**，完成才算数。

---

## 目标 1：建立真实健康基线

**完成标准**：丁丁限流恢复后，用节流代码（域名分组串行）全量重跑 96 个启用源，产出三档数据：
- 搜索可用率：X / 96
- 目录可用率：Y / 有目录规则数（失败分类：network / empty）
- 正文可用率：Z / 有正文规则数（失败分类：network / empty）

**验证**：报告数字 + 失败源完整清单（记录到本文件"结果"节）。
**预估**：1 小时。

## 目标 2：常用源全链路 100% 达标

**完成标准**：错层、丁丁、阅友、南极、番茄、疯读 6 个常用源，搜索→目录→正文全部可用（正文 ≥200 字符）。

**方法**（lessons 3.39 流程）：
1. 失败源先单源单次请求复核（排除限流干扰）
2. 判断原因：限流（等恢复）/ 反爬（补 header/cookie/Referer）/ 规则缺口（修规则）
3. 修复后单源复验 3 环节
4. 每源一条验证记录

**验证**：每源 3 环节验证记录写入本文件。
**预估**：2-3 小时。

## 目标 3：全链路检测 GUI（把测试脚本变成产品能力）

**完成标准**：书源管理新增「全链路检测」入口：
- 复用 fullChainHealth 节流逻辑（域名分组串行 + 200ms 间隔）
- 结果按 搜索失败 / 目录失败 / 正文失败 分类展示（含失败原因）
- 支持勾选批量禁用

**前置确认**：现有「批量验证」是搜索级（sourceVerify），全链路检测是目录/正文级——两者并存不冲突。

**验证**：单元测试 + 真机操作一遍（发现 1 个真实失效源并禁用）。
**预估**：2-3 小时。

## 目标 4（穿插）：悬浮工具栏体验闭环

**完成标准**：用户实测新工具栏（全宽悬浮/页码指示/字号 A±）后，反馈逐条处理，每条独立提交。

## 目标 5（弹性并行）：本地备份/恢复

**完成标准**（先本地，不做 WebDAV）：
- 设置页新增「备份与恢复」：一键导出全量 JSON（书源列表+书架+阅读进度+阅读设置）
- 一键导入恢复（覆盖确认）
- 备份文件含版本号，导入时校验兼容性

**验证**：导出→清库→导入→数据完整（书源数/书架数/进度一致）；单测覆盖导出格式与导入恢复。
**预估**：2-3 小时（仅在目标 1 卡住/等限流时并行做）。

## 优先级（2026-08-16 划分）

| 优先级 | 目标 | 理由 |
|--------|------|------|
| **P0（上午）** | 目标 1：真实健康基线 | 数据前提：不知道哪些源失败就不知道修什么 |
| **P0（上午-中午）** | 目标 2：常用源全链路 100% | 直接兑现用户价值「能搜到就能读」；依赖目标 1 清单 |
| **P1（下午）** | 目标 3：全链路检测 GUI | 产品化：以后一键排除失效源；复用 P0 验证过的节流逻辑，成本低 |
| **P2（穿插）** | 目标 4：悬浮工具栏反馈 | 弹性：用户实测反馈随时插入，无反馈不做 |
| **弹性（并行）** | 目标 5：本地备份/恢复 | 全局支柱④（数据安全）结构性缺口：书源+书架+进度+设置全量 JSON 导出/导入（先本地，不做 WebDAV）；① 卡住（等限流恢复）时顺手做 |

**全局视图**：项目支柱 ①书源生态（本次聚焦）②本地阅读 ③书架数据 ④数据安全（目标 5）⑤阅读增强（统计/TTS 细化，后续）⑥平台能力。本次迭代主攻 ①，④ 为弹性并行线。

**合并主线**：P0 = 目标 1+2（「常用源全链路达标」是上午核心产出，不可分割）。

**砍单策略**：时间不够先砍 P2 → 再不够目标 3 简化为「调试页输出报告」（不做批量禁用）→ 目标 5 只做导出（导入下一轮）。

**风险前置**：目标 1 开始前先跑 5-10 源小样本确认节流生效（丁丁可能仍限流，全量重跑需跳过该域名或等恢复）。
